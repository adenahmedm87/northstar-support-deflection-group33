# Team Charter — PentaCore
## Northstar Support Deflection MVP — PLP Group 33

## Team Purpose

PentaCore is working together to deliver the Northstar Retail Support Deflection MVP within the 5-day sprint.

Our goal is to build a simple, reliable and demonstrable customer self-service solution for:

- Order Status
- Stock Availability

The project should demonstrate genuine teamwork, clear task ownership, traceable contributions and a working end-to-end MVP.

## Daily Communication Expectations

- Every member should provide a short progress update by 8:00 PM where possible.
- Expected response time is within 4 hours between 9:00 AM and 9:00 PM.
- A member who expects a delay should inform the team as early as possible.
- Members should not remain silent when a task is blocked.

---

## Deadlines

- Deadlines are agreed when tasks are assigned on the Project Board.
- Members should flag a likely missed deadline at least 12 hours before it is due where possible.
- No silent missed deadlines.
- When a delay affects another member's task, the affected member and Team Lead should be informed immediately.

---

## Decision-Making Rules for Disagreements

The team will first try to make decisions through discussion and agreement.

When there is disagreement:

1. Team members explain their proposed solutions.
2. Options are compared against the MVP scope, assignment requirements, reliability and sprint deadline.
3. The team attempts to reach agreement.
4. If agreement cannot be reached quickly and the issue is delaying progress, the Team Lead makes the final decision based on the project requirements and delivery deadline.

Decisions should favour a simple working MVP over unnecessary complexity.

---

## Conflict Resolution

1. Raise the issue respectfully in the team communication channel.
2. The members involved first attempt to resolve the issue directly.
3. If unresolved within 24 hours, the Team Lead facilitates a discussion or short call.
4. The team agrees on a practical recovery action.
5. If the issue still cannot be resolved internally, it is escalated to the PLP instructor, facilitator or manager.

---

## Conflict Escalation Trigger and Path

### Trigger

Escalation may begin when there is:

- A missed or likely missed task
- Repeated lack of communication
- Unclear task ownership
- A disagreement affecting project delivery
- A dependency blocking another team member
- A contribution that does not meet the agreed task requirements

### Escalation Path

Trigger  
→ Step 1: Contact the responsible member directly  
→ Step 2: Raise the issue with the Team Lead  
→ Step 3: Discuss the issue with the full team and agree on a recovery action  
→ Step 4: Reassign or adjust the task where necessary  
→ Step 5: Escalate to the PLP facilitator or instructor only if the team cannot resolve the issue internally

## Branch / Edit and Commit Convention

Changes should represent genuine project work and be connected to the relevant task or GitHub Issue.

Commit messages should follow:

<type>: <what changed> - <why it matters> Issue XX

Examples:

feat: add Order Status form - allows customers to submit order requests Issue 07

data: organise sample stock records - keeps stock test data traceable Issue 06

fix: connect stock response to webhook - restores live Stock Availability responses Issue 12

docs: update go-live readiness note - records final sprint status Issue 15

Common commit types include:

- feat:
- fix:
- data:
- docs:
- test:

Members should avoid unclear commit messages such as:

- update
- changes
- work
- final
- WIP

Where direct edits to the main branch are used, the GitHub Issue, commit message and Project Board should still make the contribution traceable.

---

## Task Ownership

Each task should have:

- A clear owner
- A related GitHub Issue
- A board status
- A meaningful commit or revision where applicable
- Evidence of completion

Members should primarily complete work assigned to their role.

If another member helps troubleshoot a task, the responsible member should still make a genuine contribution where possible so the audit trail reflects real collaboration.

---

## Team Working Principles

We agree to:

- Communicate respectfully
- Help one another when blockers occur
- Keep contributions honest and traceable
- Avoid taking credit for another member's work
- Keep the MVP within the agreed scope
- Prioritise working features over unnecessary additions
- Test changes before final submission
- Keep GitHub Issues and the Project Board updated
- Raise problems early instead of hiding delays
- Complete individual assignment requirements honestly

---

## Definition of Done

A task is considered complete when:

- The required work has been implemented
- The work has been checked or tested where appropriate
- The related GitHub Issue has been updated
- The contribution is visible in the audit trail
- The Project Board status reflects completion
- The change does not break previously working MVP features
